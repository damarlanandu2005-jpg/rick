## B. Findings that change the picture
1. **The Blender executor already exists.** `templates/blender_look/from_lock.py` (READ): builds the camera from `camera_baked.json` one key per frame (vertical fov, DOF focus on the subject's card), places one card plane per character with the drawing swapped per frame from `index.json`, imports the locked set `.glb` and swaps every `mat:<tag>` material for the library material of that name, computes `keep_clear` discs for dressing, and refuses to run if the plan changed after the lock (sha1). Our Pass A used only a fragment (`from_lock.card`). My spec's "new executor required" (section 10 item 1) was wrong.
2. **Attachment is solved by hand points, not new sockets.** `pieces/fx/fly_and_hit.js` (READ): "from = the muzzle point in a real hand, on the frame the hand fires; to = where it sticks"; a timetable gives leave and hit frames; the piece is "technique as numbers, no three.js", applied by the set module. `cards/meta.json` hand offsets exist. So "sockets" were my invention.
3. **Set authoring in Ricks is a small three.js module per place** (`sets/platform.js` is 50 lines for the demo) tagged with `mat:` names that Blender converts. Blender then adds materials, light, air and dressing (`scatter` with keep-clear). Our `kit/` (set recipe + scatter + density gate) therefore fits as the Blender dressing stage on top of a simple locked layout, not as a replacement for the layout stage.
4. **The cheap loop works here with no GPU**: planning (0.2 s), storyboard (19 s), visibility (1.5 s), frame checks (4 s), lock (31 s). Only the full animatic is slow here (about 1 s/frame).
5. **The checkers find real defects.** frame_checks caught a cut head in Ricks' own demo in 4 s. check_film disagrees with plan check on two numbers: the gates are not interchangeable and the example is not clean.
6. **Pitfall notes (4 read)** are concrete pre-flight tests that Ricks mostly already bakes into the plan or the checkers (e.g. keys mean *arrive* with `lead` 5 frames; horizontal fov in 9:16 is narrow, stage in depth; stale camera near/far; body inside furniture = `body_in_mesh` check).
7. **Blender 5.x compatibility (READ, not run):** `from_lock.py` already handles layered actions (4.4+/5.x) with a `fcurves` fallback and uses `surface_render_method` with a fallback. `cine.py` guards `action.fcurves` with `hasattr`, so on 5.x the interpolation-fix block is silently skipped (effect on easing unknown until run in Blender). `blender_look` ran on Colab 5.2.4 in our rounds (look, grade, lights, scatter, from_lock.card). `cine.py` has not run in our Blender.
8. **Effects**: `film.json` `fx` play as placeholder rings in three.js; the real effect is look-pass work in Blender from `FX.md` recipes. Blender effect recipes remain a genuine gap; timing numbers come from the pieces.

## H. Moving-object camera / chase-camera forensic result
**Source files inspected (code, not only docs):** `tools/film_plan.py` (696 lines: `_bake`, `bake_performance`, `perf_at`, `camera_segments`, `_ev_val`, `solid_seg`, kicks), `templates/threejs_film/film.js` (camera, `propPos`, anchors, placeholder fx, highlights, lock), `templates/blender_cine/cine.py` (257 lines, all of it), `templates/blender_look/from_lock.py` (camera, card, build), `templates/pieces/camera/camera_pieces.json`, `templates/pieces/fx/fly_and_hit.js` (header and timetable), CINEMATOGRAPHY sections 3–5; `grep` of every file for who calls the rigs.

**H1. Actual data flow (traced).**
- `film.json` station (`at, pos, aim, lens, subject, framing, shows, hold, travel, via, follow, follow_k, roll, creep…`) → `film_plan._bake` evaluates per frame: rest pose with creep, then a Catmull-Rom travel between stations with smootherstep and log-lens zoom, plus kicks → `camera_baked.json` (per frame pos, aim, up, roll, lens, fov_v, state, subject…).
- three.js (`film.js`) reads `camera_baked.json` only ("owns NO camera maths"). `from_lock.camera()` reads the same file and keys the Blender camera every frame (LINEAR, easing already baked). So station cameras are identical in the plan, the three.js preview and Blender.
- `cine.py` is a SEPARATE camera system: Python functions of the frame number, baked with `Shot.bake()` into Blender keyframes. Nothing outside `cine.py` calls it (grep over the whole repo: only `cine.py`, its `__init__`, and a measuring tool that merely has "cine" in its name). `film_plan.py`, `film.js`, `render.mjs`, `from_lock.py` have no handling of "rig" or "recipe", although the camera-director brief says film.json carries "rig recipes for action beats". That sentence is documentation only: no schema, validator or reader exists.

**H2. Can a station follow a moving thing? Executed test.** Scratch copy of the example film, kid given two acts (frame 151 at x −2.0, frame 160 at x −0.5), station 4 with and without `"follow": "kid"`: camera x at f162 is −1.3418 without follow and −1.0446 with follow; the difference +0.2972 equals the kid's baked displacement (−2.0 → −1.7028) × `follow_k` 1.0. So **YES for a cast character**: the station camera trucks with that character's baked position (`perf_at(perf[who], f)`), through plan, three.js and Blender, identically. **NO for anything that is not in `performance_baked`**: props in film.json are static (`pos`) or `held_by` a character; `places.<p>.events` animate set objects between two values (smootherstep, used for levers); film_plan never reads set-module `anchors`.

**H3. Moving anchors in three.js.** A set module's `anchors` may be a function of the frame (`typeof an === 'function' ? an(f) : an`, film.js lines 178 and 454; `propPos` line 474). Placeholder `fx` (`on: <anchor>`) and highlights therefore can sit on a moving anchor in the preview, and `kicks` (7-frame sign-flipping shake) are implemented in the plan bake. But that motion lives in the set's JavaScript, after the plan is baked, so the plan's camera cannot reference it. It is a preview aid for effect timing, not a camera target.

**H4. The projectile rule, step by step.**
| Rule step | Status in code |
|---|---|
| object followed + where its position comes from | In Blender: `object_path(obj,f0,f1)` samples the evaluated world transform of ANY animated object each frame (needs bpy); `ballistic_path(p0,v0,g,f0,heading)` is analytic (hand check: p0 (0,0,1.2), v0 (0,0.5,0.05) m/frame, g 9.81/900, f=10 gives (0, 5.0, 1.155)); `line_path`, `spline_path`, `loop_path` likewise. In the plan: only cast characters. |
| camera can reference a target that moves | Blender: yes, every rig takes a path function. Plan/three.js: characters only. |
| camera path baked per frame | both systems bake per frame (camera_baked.json; `Shot.bake` keyframes) |
| slow push | plan: station `creep`/travel (implemented); Blender: `push` rig (implemented) |
| contact 0–3 f before the word | times in film.json accept [word,n,offset]; `fly_and_hit.timetable` gives leave and hit frames as numbers (pure JS, runs); no code connects a projectile's hit frame to a word in the plan |
| 7-frame kick | implemented in the plan (`kicks`) and in `Shot.shake` |
| ≤2-frame flash | placeholder ring only in three.js (default 0.8 s); a real flash is Blender look-pass work (no recipe in the package) |
| pull-out | station travel (implemented) or `catch`/`static` in cine |
| three.js can preview | stations, character follow, word timing, kick, fx timing on a moving anchor; NOT a chase of a moving projectile |
| Blender can reproduce | yes, by a hand-written per-shot script as in CINEMATOGRAPHY §5 (path, `Shot.add(...)` rigs with blends, shake, roll, bake) |
| existing film.json schema sufficient | not for a moving non-character object: it has no field for a flight (from, to, leave, hit) and no field that makes the camera follow one |

**H5. Classification (A implemented / B documented / C partly).** Evidence read from code: `object_path`, `ballistic_path`, `mix_path`, `line_path`, `spline_path`, `loop_path`, `chase`, `mount`, `orbit`, `catch`, `static`, `push`, `Shot.add/shake/roll/bake`, `motion_blur`: all **implemented machinery inside Blender**, not only text. Their connection to `film.json` and to the three.js preview: **manual** (a per-shot Python script written by the director). So: path and rig library = implemented (Blender only); integration with the plan = absent/manual. Not run here: `cine.py` needs `bpy`/`mathutils`, so its numbers come from reading, plus the one hand check above. Ricks' proof shot for it (`episodes/_test_cine_loop`) is not in the zips.

**H6. What three.js can prove and what only Blender can.**
- three.js (all measured above or read): layout and set coverage; character staging and views; station camera moves and rests including following a character; word timing of acts, faces, kicks, fx; head cuts, feet, geometry between lens and face, visibility (frame checks, 4 s); composition in 9:16; the plan's rhythm gates; fx timing on a named, even moving, set anchor.
- Only a Blender animatic (or final): a camera chasing, mounted on, orbiting or catching a moving object; a flight path's real 3D positions and the frame on which it leaves and lands as seen by the lens; real flash, light, smoke, dust; motion blur; depth of field on the chase; whether the world "streams" past (needs texture near the path); the real look of the set.
- Not provable by either yet: that a projectile is in frame on its hit frame and the camera is where the rule says, because no code ties a projectile to the camera in the plan.

**H7. Does the existing Ricks architecture need modification?** Not its architecture: the station camera, baked plan, lock and `from_lock` stay as they are. One genuine gap: the bridge between a film.json-level description of a moving non-character thing and the existing Blender path/rig machinery. Smallest missing implementation, without designing it: a way to state a flight once (from point, to point, leave and hit frames or words) so a Blender executor can build its path and call the existing rigs, and so a three.js set can place the same thing on the same frame. Everything else in the projectile rule already exists.

**H8. Verdict.** **Option B**, with a C at the seam. Ricks implements moving-object cameras (paths, chase, mount, orbit, catch, mix_path, kick, blends) in Blender, and following a character in the plan; it does not support a moving non-character target in the plan or the three.js preview, and the film.json-to-rig connection is manual. Keep three.js as layout, station-camera, acting, word-timing and frame-check proof. Use a cheap Blender animatic for the moving-object shots (Ricks' own figure: about 1 s per frame at 25 % size, 8 samples; not measured on Colab T4). Whether to close the seam with a small shared flight description or to keep writing the per-shot rig script by hand is a decision for you; it is not required by any Ricks code.

## I. One Blender camera, two writers? (traced in code; cine.py not run: needs bpy)
| Aspect | `from_lock.camera()` | `cine.Shot.bake()` | Compatible? |
|---|---|---|---|
| Camera object | creates "FilmCam", sets `scene.camera` | takes ANY camera object passed to `Shot(scene, cam, f0, f1)` | yes: `Shot` can be given `K["camera"]` |
| Channels keyed | location, rotation_quaternion, lens, dof.focus_distance, one key per frame | the same four, one key per frame | same channels |
| Sensor model | `sensor_fit VERTICAL`, height 24 mm, lens from `fov_v` | assumes vfov = 2·atan(12/lens), i.e. 24 mm vertical | consistent |
| Rotation convention | `Matrix((r, u, -f)).transposed().to_quaternion()` | `Matrix((right, up, -fwd)).transposed().to_quaternion()` | identical |
| Overlap behaviour | keys every frame of the place | `keyframe_insert` on an existing frame overwrites it | later writer wins per frame; no arbitration |
| Interpolation | sets every key LINEAR (using a layered-action fallback) | sets LINEAR only if `action.fcurves` exists (`hasattr`); skipped on 5.x | mixed interpolation possible on 5.x (unverified) |
| Focus | `camera_focus` second pass from the subject's card | focus from the rig's subject | later writer wins |
| Entry/exit of a cine range | n/a | rig-to-rig blends only (`Shot.add(blend)`); nothing blends plan camera → rig | possible jump at the range edge unless the first rig matches the plan pose (unverified) |
| Protection | sha1 of `camera_baked.json` checked at `read()` | none | the sha1 does not cover cine's keys |
| Seen by three.js, frame checks, `film_plan` gates, `visibility` | yes (they read the baked file) | no | cine camera exists only inside Blender |
Result: **technically one camera object can be fed by both**, but as written they are two competing writers and only the plan camera is the source other tools see. Observation only: `Shot.eval(f)` returns the per-frame pose as plain data (pos, aim, up, roll, lens, focus); `bake()` adds an aim-lag spring, kicks and rolls and then keys them. So the same result could in principle exist as per-frame data instead of Blender keys. Not designed here.

## J. What "lock" means (read from `render.mjs --export-lock`, `film.js` lock section, `from_lock.py`, SKILL stage 8)
1. **Frozen by the lock:** per place a `.glb` of the set in its frame-0 pose with a `lock_id` on every node and `mat:<name>` material tags plus base colours; `motion/<place>.json` = per-frame transform (position, rotation, scale, opacity) of every set node that the set's `update(f,t)` moves (the example holds 2 clock hands × 460 frames); character card drawings (one PNG per unique state, 1600×3000) with `index.json` runs (which image, where, visible, flipped, per frame range); per-place light settings (`lights`: sky colours, sun colour/intensity/direction, ambient); `highlights.json`, `instances.json`; fps, frames, size, coordinates note; and `sha1` of `camera_baked.json` and `performance_baked.json` (those two live in `out/plan`, they are pinned, not copied).
2. **Allowed to be generated later:** materials (library), light, air, mist, dressing (scatter with keep-clear), effects, grade, render settings. SKILL stage 8: "no layout, camera or timing change after this"; `from_lock` docstring: "the only things the look pass adds are materials, light, air and effects".
3. **What `from_lock.py` actually consumes:** from `lock.json` only `sha1`, `cards`, `fps`; from `out/plan` the camera frames; from the lock folder the `.glb` and the card folders. It does NOT read `lights`, `motion`, `highlights`, `instances` or `overlay`. (Searching the whole repo, no Python reads them; SKILL says per-episode look scripts use `instances.json`, and those scripts are not delivered.) So the lock contains more than the delivered consumer uses.
4. **Could a flight be frozen before Blender while `cine.py` generates the camera?** The lock's contract forbids camera changes after it, and its guard covers only the two plan files. A cine-generated camera would sit outside that guard and outside what three.js and the plan gates see. A flight described before the lock is consistent with the lock; a camera generated afterwards is not, unless it becomes part of what the lock pins.
5. **Where the single source of truth lives, by Ricks' own design:** `film.json` → baked files in `out/plan` (derived, never hand-edited) → read by three.js, by `from_lock`, and by the checkers. The camera has exactly one source there.

## L. FINAL FORENSIC REPORT
**A. Confirmed Ricks architecture.** One plan table (`film.json`) → `film_plan.py` bakes camera, performance and sound events into `out/plan` and runs 41 gates → three.js plays only the baked files (storyboard, animatic, visibility, frame checks) → `--export-lock` freezes sets, cards, lights, moving-set motion and pins the two plan files by sha1 → `from_lock.py` rebuilds camera, cards and set in Blender → look pass adds materials, light, dressing, effects → render → pixel-based measure tools → sound → post. A second, Blender-only action-camera library (`cine.py`) exists beside it with no link to `film.json`.
**B. Confirmed three.js responsibilities.** Layout; character staging and views; station camera moves including following a character; word timing of acts, faces, kicks, placeholder fx (also on a moving set anchor); head cuts, feet, visibility; composition; lock export. Not: moving-object chase cameras, real light, effects, final look.
**C. Confirmed Blender responsibilities.** Camera per frame from the baked plan; cards with per-frame drawing swaps; set import with library materials; light, air, dressing, effects, grade; the action camera and path library (`cine.py`); final render. `blender_look` ran in our Colab rounds on 5.2.4; `cine.py` and `from_lock.camera` have not.
**D. Confirmed moving-object gap.** No code lets the plan, the three.js preview or `film.json` describe a moving non-character object, and none connects its flight to the camera, a hit frame, or a word. Also: the lock freezes per-frame motion of moving set nodes, but no delivered code consumes it. The rig library is implemented but reached only by hand-written Blender scripts.
**E. Remaining unknowns.** Whether `cine.py` and `from_lock` run together on Blender 5.2.4 (interpolation, range-edge jumps); whether undelivered per-episode look scripts consumed `motion`, `lights`, `highlights`, `instances`; GPU animatic speed on Colab; real effect recipes (flash, trail, dust) for Blender; the sample library and the `sound_events` → mix wiring; about 12,000 words of CB_RULES fine print (sections 3, 8, 9, 10 beyond the first ~200 characters per rule); `film.js` shading internals; whether a non-character thing can be a cast entity (not tested).
**F. Lock semantics.** See section J: it pins layout, timing and camera (via sha1) and freezes set, cards, lights and moving-set motion; it permits only look additions afterwards; the delivered `from_lock` reads far less of it than it stores.
**G. Before or inside the lock?** Evidence says before. A flight fixes where something is on which frame, which decides the camera, the hit frame and the effect timing: all layout/timing facts that the lock forbids changing and that already live in plan data (`fx`, `kicks`, `moods`). Only the realisation of the flight (bullet model, trail, flash, light) is look-pass work after the lock.
**H. Extend `film.json` or a separate artifact?** Ricks' convention is inline keys in `film.json` for anything the plan must read (`solids`, `places.<p>.events`, `hand_at`, `kicks`, `fx`, `moods`, `transitions`, `props`), with camera pieces shipped as film.json snippets; separate files are used for the voice (`words.json`) and for derived outputs. So the evidence favours a key inside `film.json`. The structure of that key is not designed here.
**I. Exact minimum bridge needed** (requirements only): (1) the plan side can read a statement of a flight (what, from where, to where, leave and hit moments tied to frames or words); (2) the final camera has one writer: either existing station data, or rig-generated per-frame data stored in the same baked-camera format so `from_lock`, three.js and the checkers keep reading one file; (3) a Blender step that places the flown object on that flight from the same data; (4) the existing effect, kick and station machinery referencing that flight by name. Nothing else.
**J. Things we should NOT build.** A new camera engine; a new Blender executor; sockets; a replacement for `cine.py` or `from_lock`; a second independent camera source; per-shot hand-written Blender scripts as the final architecture; a new lock format; new validators where measure tools already exist; a rewritten audio engine (reuse DSP/meter, add the missing wiring only when sound is in scope).
